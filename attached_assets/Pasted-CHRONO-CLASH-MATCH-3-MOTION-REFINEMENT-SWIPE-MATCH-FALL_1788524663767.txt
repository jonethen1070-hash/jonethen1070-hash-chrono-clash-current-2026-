==================================================
A. SWIPE — TRUE DIRECT MANIPULATION
==================================================

This is the highest priority.

The selected gem must be physically attached to the finger.

DO NOT use:

pointerdown
→ wait
→ threshold
→ play a fixed swap animation

Instead:

pointerdown
→ immediately capture gem
→ pointermove continuously updates visual gem position
→ finger controls gem position
→ neighboring gem responds
→ threshold crossed
→ exchange begins from CURRENT visual positions
→ magnetic settle into socket

Coordinate model:

For each selected gem:

cellCenterX = boardOriginX + col * cellSize + cellSize / 2
cellCenterY = boardOriginY + row * cellSize + cellSize / 2

During drag:

dragX = pointerX - grabOffsetX
dragY = pointerY - grabOffsetY

Clamp the drag vector to the selected neighboring-cell direction.

The gem's rendered position must be derived from this drag position EVERY FRAME.

Do NOT wait for pointerup.

Do NOT animate from the original cell after the threshold.

==================================================
B. DRAG RESPONSE
==================================================

Use extremely light smoothing only.

Target:

visualPosition += (targetPosition - visualPosition) * responseFactor

Use a frame-rate independent response.

Approximate response time:
20–35ms.

The player should NOT perceive the renderer chasing the finger.

Do NOT use heavy lerp smoothing such as 100ms+.

Slow finger:
→ gem moves slowly with finger.

Fast finger:
→ gem responds immediately.

Reverse direction:
→ gem reverses naturally.

The finger is the source of truth.

==================================================
C. CELL-SCALE GEOMETRY
==================================================

Do not make the gem move more than the neighboring cell.

For a horizontal drag:

normalizedDrag = clamp(
  (pointerX - startX) / cellSize,
  -1,
  1
)

For vertical:

normalizedDrag = clamp(
  (pointerY - startY) / cellSize,
  -1,
  1
)

The selected gem may visually travel continuously through:

0.0 → 0.25 → 0.5 → 0.75 → 1.0 cell

rather than jumping directly:

0 → 1.

This is essential.

==================================================
D. NEIGHBORING GEM RESPONSE
==================================================

The neighboring gem must respond continuously as the selected gem approaches it.

Example:

selected gem = A
neighbor = B

As A moves toward B:

A position:
0.00 → 0.20 → 0.40 → 0.60 → 0.80 → 1.00

B position:
1.00 → 0.80 → 0.60 → 0.40 → 0.20 → 0.00

Do not allow B to disappear and reappear.

Both visual positions must interpolate continuously.

==================================================
E. SWAP COMMIT
==================================================

When the existing valid threshold is crossed:

Commit the logical board exchange.

BUT preserve the current visual positions.

The visual animation must continue FROM:

CURRENT DRAG POSITION

not from:

ORIGINAL SOCKET CENTER.

This is critical.

Bad:

original socket
→ reset
→ tween
→ destination

Good:

finger position
→ current crystal position
→ smooth continuation
→ destination socket

==================================================
F. MAGNETIC SOCKET SETTLE
==================================================

Use a short final magnetic settle.

Target:
60–90ms.

Only the final ~10–15% of travel should use this magnetic easing.

Use a smooth cubic ease-out / critically damped style.

No hard snap.

No overshoot.

No bounce.

No sudden acceleration.

The crystal should feel like it is being attracted into a precision socket.

==================================================
G. INVALID SWAP
==================================================

If the move is invalid:

Do not teleport the gem back.

Animate from the CURRENT finger-driven position back to the original socket.

Target:
140–180ms.

Use smooth ease-out.

The player should feel:

"I pushed it, but the board rejected it."

Not:

"The gem disappeared and returned."

==================================================
H. MATCH TRANSITION
==================================================

After a successful swap:

DO NOT abruptly switch from movement to destruction.

Required sequence:

SWAP FINISH
↓
SOFT SOCKET SETTLE
↓
MATCH RECOGNITION
↓
CRYSTAL REACTION
↓
BREAK
↓
REMOVE
↓
FALL

Match recognition:

60–90ms.

During recognition:
- tiny compression
- internal brightness
- facet emphasis
- subtle energy pulse

Do NOT freeze the entire board.

==================================================
I. CRYSTAL BREAK
==================================================

The gem should not simply disappear.

Target:

100–150ms destruction presentation.

Use the existing VFX infrastructure.

Sequence:

0–40ms:
compression / energy buildup

40–90ms:
fracture / facet flash

90–150ms:
crystal fragments + small energy particles

Then remove the gem.

The break must feel like the crystal itself is breaking.

Not:

opacity → 0

==================================================
J. MATCH GROUP TIMING
==================================================

Do not destroy every matched gem on exactly the same frame.

Use a tiny stagger:

10–25ms between nearby matched gems.

Example:

Gem 1:
0ms

Gem 2:
15ms

Gem 3:
30ms

This creates a connected chain reaction.

Do NOT make the stagger slow enough to feel sequential or laggy.

==================================================
K. FALLING — PRESERVE CURRENT LOGIC BUT REFINEMENT MUST BE DISTANCE BASED
==================================================

Do NOT redesign the existing gravity system.

However, verify that each gem's visual fall is based on DISTANCE TRAVELLED, not one generic duration.

Movement distance:

1 cell
2 cells
3 cells
4 cells
5 cells

should produce proportionally longer travel.

Use a consistent fall-speed model.

Target starting range:

approximately 150–220ms per cell,

then tune from LIVE DEVICE observation.

Do NOT make a 5-cell fall take the same time as a 1-cell fall.

Do NOT animate a 4-cell fall as four separate stop/start one-cell animations.

Calculate each gem's complete destination and animate the full trajectory continuously.

This is critical for smoothness.

==================================================
L. FALL CURVE
==================================================

Use a physically readable gravity curve.

Recommended model:

normalizedTime = t / duration

position = start + distance * easeOutQuadratic(normalizedTime)

or an equivalent smooth gravity-inspired curve.

The gem should:

START:
controlled

MIDDLE:
accelerate naturally

END:
decelerate into the socket

Avoid:
- linear movement
- sudden velocity changes
- multiple micro-tweens
- robotic stepping

==================================================
M. LANDING
==================================================

When a falling gem reaches its destination:

Use a very subtle landing response.

Approximately:

scale:
1.00 → 1.015 → 1.00

duration:
40–60ms

Optional:
1px visual settle.

Do NOT bounce aggressively.

The landing should feel weighted, not cartoonish.

==================================================
N. CASCADE CONTINUITY
==================================================

When falling produces another match:

Do not create a visible dead stop.

Required:

fall
→ land
→ match recognition
→ break
→ next fall

The next cascade should feel like the same physical system continuing.

Avoid:

fall
→ FREEZE
→ sudden explosion

==================================================
O. FRAME-RATE INDEPENDENCE
==================================================

All motion must be based on elapsed time, not frame count.

Use:

deltaTime

or equivalent time-based interpolation.

The result must remain consistent at:

30fps
60fps
90fps
120fps

Do not make animation speed dependent on frame rate.
