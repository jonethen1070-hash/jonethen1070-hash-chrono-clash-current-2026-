I want to make the existing Chrono Clash project AI-friendly and maintainable BEFORE doing any more visual or gameplay upgrades.

This is an ARCHITECTURE / OWNERSHIP REFACTOR.

Do not redesign the game.
Do not add new gameplay.
Do not change the visual style.
Do not change the board size.
Do not change the 8×8 grid.
Do not change gems.
Do not change touch/swipe behavior.
Do not change HUD layout.
Do not change abilities.
Do not change networking/authentication/persistence.

The goal is:

EVERY IMPORTANT GAMEPLAY OR VISUAL FEATURE MUST HAVE ONE CLEAR SOURCE OF TRUTH AND ONE OBVIOUS FILE/PATH THAT AN AI AGENT CAN MODIFY.

CURRENT PROBLEM TO SOLVE:

The project currently has overlapping responsibilities and large amounts of cascading CSS.

In particular:
- main.ts contains substantial UI/game wiring
- session.ts contains gameplay/session logic
- renderer.ts contains Canvas rendering
- game.css, studio.css and aaa-polish.css all contribute to presentation
- aaa-polish.css is extremely large and contains repeated/overriding board selectors
- the player board uses both DOM/CSS hardware layers and Canvas rendering
- some later CSS rules can hide or override earlier visual changes
- gameplay behavior and UI descriptions can become disconnected

DO NOT ASSUME THE CURRENT ARCHITECTURE IS CORRECT.

Create a clear ownership model WITHOUT breaking the existing game.

Use the smallest safe number of modules.

The desired conceptual ownership is:

BOARD GAMEPLAY
→ one authoritative board/game-state module

POWERS
→ one authoritative power/ability module

INPUT
→ one authoritative input/swipe module

SESSION
→ one authoritative match/session orchestrator

RENDERING
→ one authoritative rendering path

BOARD FRAME
→ one authoritative visual owner

GEMS
→ one authoritative gem-rendering owner

HUD/UI
→ one authoritative UI owner

VISUAL STYLE
→ one authoritative stylesheet/component per visual system, rather than endless override chains

Do not blindly create files just to create files.

If an existing file is already the correct owner, keep it.

If functionality must move, move it carefully and update all imports/callers.

THIRD PHASE — CONSOLIDATE

Safely remove or consolidate duplicate implementations.

The board frame must have ONE authoritative implementation.
